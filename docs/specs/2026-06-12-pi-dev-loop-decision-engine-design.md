## 1. Problem Summary

The current implementation has all module scaffolding in place (state.ts, error-registry.ts, subagent-task.ts, session-prompt.ts, verify-config.ts, index.ts) **but the core loop does not actually drive decisions**:

| Problem | Root Cause |
|---------|------------|
| `dev_control("next")` doesn't update error registry | `mergeRegistry` never called |
| `detectProgress` never called | No integration point wired |
| `verificationPassed` ignored | No guard in decision logic |
| Subagents return text, not structured errors | No output protocol defined |
| Review critical findings not promoted to error registry | No auto-conversion |
| No `.pidev.yml` config file support | No YAML parser |
| No `{files}` template expansion | No substitution pass |
| No git snapshot/rollback | No git.ts module |
| `ask_user` verifier not functional | No pause/resume for user interaction |
| Sparse TUI widget | No error summary in widget |
| No `/dev history` | No reconstruction logic |

## 2. Architecture: Structured Subagent Output Protocol

### 2.1 Impl Subagent Structured Output

Every impl subagent task (generated by `packImplTask`) now includes a mandatory structured output section at the end. The subagent **must** return a JSON block matching this schema:

```typescript
interface ImplSubagentOutput {
  changedFiles: string[];              // Files modified in this task
  verificationPassed: boolean;         // All required verify commands passed
  summary: string;                     // Human-readable summary
  errorsFixed: ErrorSignature[];       // Errors that were present and are now fixed
  errorsRemaining: ErrorSignature[];   // Errors that persist after this iteration
}
```

Where `ErrorSignature` is:

```typescript
interface ErrorSignature {
  id: string;           // fingerprint(file, line, message)
  category: "type" | "lint" | "test" | "compile" | "runtime" | "review";
  file: string;
  line?: number;
  message: string;
}
```

### 2.2 Review Subagent Structured Output

```typescript
interface ReviewSubagentOutput {
  findings: Array<{
    severity: "critical" | "important" | "minor";
    file: string;
    message: string;
  }>;
}
```

### 2.3 dev_control Input Type Extension

The `implSubagents` parameter of `dev_control` gains two new fields:

```typescript
interface ImplSubagentReport {
  id: string;
  task: string;
  changedFiles: string[];
  verificationPassed: boolean;
  summary: string;
  errorsFixed: ErrorSignature[];      // ← NEW
  errorsRemaining: ErrorSignature[];   // ← NEW
}
```

### 2.4 End-to-End Data Flow

```
┌─ Impl Subagent ─────────────────────────────────┐
│ Receives task with structured output requirement  │
│                                                    │
│ After TDD + verification:                          │
│ Returns text response containing JSON block         │
│ (last section of response, delimited by ```json)    │
└──────────────────────┬─────────────────────────────┘
                       │
                       ▼ (orchestrator LLM reads response)
┌─ Main Session LLM ───────────────────────────────┐
│ Extracts changedFiles, verificationPassed,         │
│ errorsFixed, errorsRemaining from subagent output  │
│                                                     │
│ Passes extracted data to dev_control() call:        │
│   dev_control({                                     │
│     implSubagents: [{                               │
│       errorsFixed: [...],                           │
│       errorsRemaining: [...],                       │
│       ...                                           │
│     }]                                              │
│   })                                                │
└──────────────────────┬─────────────────────────────┘
                       │
                       ▼
┌─ dev_control tool ───────────────────────────────┐
│ Receives structured fields,                        │
│ calls mergeRegistry + detectProgress,              │
│ updates state                                     │
└───────────────────────────────────────────────────┘
```

The main session LLM is already the intermediary that unpacks subagent responses and calls `dev_control`. The new fields (`errorsFixed`/`errorsRemaining`) follow exactly the same pattern as the existing `changedFiles`/`summary` extraction.

### 2.5 packImplTask Instruction Update

The task template in `src/subagent-task.ts` appends a structured output section after the requirements:

````
### Structured Output Format
When your work is complete, the **last section** of your response must be a JSON block:
```json
{
  "changedFiles": [...],
  "verificationPassed": true/false,
  "summary": "...",
  "errorsFixed": [{"id", "category", "file", "line", "message"}, ...],
  "errorsRemaining": [{"id", "category", "file", "line", "message"}, ...]
}
```
- `errorsFixed`: confirmed from verification command output
- `errorsRemaining`: errors still present after verification
````

### 2.6 Auto-Converts `errorsFixed` → Registry

Errors in `errorsFixed` are **not** immediately marked fixed in the registry. Instead, they are treated as "not present in current incoming" during `mergeRegistry`, which naturally transitions open records to `status: "fixed"`. This avoids double-counting.

`errorsRemaining` entries are merged into the incoming error set and flow through the normal mergeRegistry lifecycle.

## 3. dev_control Decision Engine

### 3.1 Full Flow (status "next")

```
dev_control("next", { implSubagents, reviewFindings })
                            │
                            ▼
  ┌──────────────────────────────────────────────────┐
  │ 1. VERIFICATION CHECK                             │
  │    ALL implSubagents[].verificationPassed === true │
  │    → NO: reject, do NOT advance, keep registry    │
  │      unchanged, return blockReason:               │
  │      "verification_failed"                        │
  └──────────────────────┬───────────────────────────┘
                         │ YES
                         ▼
  ┌──────────────────────────────────────────────────┐
  │ 2. COLLECT REVIEW FINDINGS                        │
  │    Push all findings to state.reviewFindings       │
  │    For severity === "critical":                   │
  │      Create ErrorSignature via fingerprint()       │
  │      category: "review"                           │
  │      Add to incomingErrors[]                      │
  └──────────────────────┬───────────────────────────┘
                         ▼
  ┌──────────────────────────────────────────────────┐
  │ 3. COLLECT INCOMING ERROR SIGNATURES              │
  │    For each implSubagents[i]:                     │
  │      Add errorsRemaining[] to incomingErrors[]     │
  │      (errorsFixed[] is NOT added — they're gone)  │
  └──────────────────────┬───────────────────────────┘
                         ▼
  ┌──────────────────────────────────────────────────┐
  │ 4. PRESERVE OLD STATE for detectProgress          │
  │    oldErrorRegistry = [...state.errorRegistry]    │
  └──────────────────────┬───────────────────────────┘
                         ▼
  ┌──────────────────────────────────────────────────┐
  │ 5. MERGE REGISTRY                                 │
  │    state.errorRegistry = mergeRegistry(           │
  │      oldErrorRegistry,                            │
  │      incomingErrors,                              │
  │      state.currentStep,                          │
  │    )                                              │
  └──────────────────────┬───────────────────────────┘
                         ▼
  ┌──────────────────────────────────────────────────┐
  │ 6. DETECT PROGRESS                                │
  │    progress = detectProgress(                     │
  │      oldErrorRegistry,                            │
  │      state.errorRegistry,                         │
  │      state.consecutiveZeroProgress,               │
  │      state.config,                                │
  │    )                                              │
  └──────────────────────┬───────────────────────────┘
                         ▼
  ┌──────────────────────────────────────────────────┐
  │ 7. DECISION BRANCH                                │
  │                                                   │
  │  REGRESSION:                                      │
  │    pauseReason = "regression"                     │
  │    active = false                                 │
  │    if guardrails.rollbackOnRegression             │
  │      && lastCleanSnapshot:                        │
  │      rollbackToSnapshot(lastCleanSnapshot)        │
  │    Return: ⚠ 回归，暂停                          │
  │                                                   │
  │  ZERO-PROGRESS:                                   │
  │    consecutiveZeroProgress++                      │
  │    if >= config.maxConsecutiveZeroProgress:       │
  │      pauseReason = "zero-progress"                │
  │      active = false                               │
  │      Return: ⚠ 零进展，暂停                       │
  │    else: advance → Step 8                         │
  │                                                   │
  │  PROGRESS:                                        │
  │    consecutiveZeroProgress = 0                    │
  │    advance → Step 8                               │
  └──────────────────────┬───────────────────────────┘
                         ▼ advance
  ┌──────────────────────────────────────────────────┐
  │ 8. CHECK COMPLETION                               │
  │    openErrors = errorRegistry                     │
  │      .filter(e => e.status !== "fixed").length    │
  │    openFindings = reviewFindings                  │
  │      .filter(f => f.status === "open").length     │
  │                                                   │
  │    if openErrors === 0 && openFindings === 0:     │
  │      auto done                                    │
  │    else:                                          │
  │      state.currentStep++                          │
  │      if currentStep >= maxIterations:              │
  │        pauseReason = "max-iterations"             │
  │        active = false                             │
  │      else:                                        │
  │        schedule next iteration via steer           │
  └──────────────────────────────────────────────────┘
```

### 3.2 Flow (status "done")

Straightforward: mark loop complete, record `reasonDone`, update widget, return.

### 3.3 State Snapshot Persistence

After each `dev_control` invocation, the snapshot (returned via `details.state`) is stored in the session branch. On `session_start`/`session_tree`, the state is reconstructed from the last `dev_control` tool result in the branch. This already works in the current code—no changes needed.

## 4. Configuration File Loading

### 4.1 `.pidev.yml` Format

```yaml
# .pidev.yml
loop:
  mode: goal                          # goal | passes | pipeline
  maxIterations: 20
  maxConsecutiveZeroProgress: 3

verify:
  - command: "bun run typecheck"
    runsOn: impl
  - command: "bun run test -- --related={files}"
    runsOn: impl
    timeout: 120000
  - command: "ask_user"
    runsOn: main
    question: "请确认当前改动是否符合预期"

guardrails:
  gitAutoSnapshot: true
  rollbackOnRegression: true
  maxFileChangesPerSubagent: 20
```

### 4.2 New Module: `src/load-config.ts`

```typescript
// src/load-config.ts
// Load DevLoopConfig from .pidev.yml
import { parse } from "js-yaml";
import { readFileSync, existsSync } from "node:fs";
import { join } from "node:process";
import type { DevLoopConfig } from "./state";

interface RawConfig {
  loop?: { mode?: string; maxIterations?: number; maxConsecutiveZeroProgress?: number };
  verify?: Array<{ command: string; runsOn?: string; timeout?: number; parser?: string; question?: string }>;
  guardrails?: { gitAutoSnapshot?: boolean; rollbackOnRegression?: boolean; maxFileChangesPerSubagent?: number };
}

export function loadConfigFromFile(path?: string): DevLoopConfig | null;
export function findConfigInCwd(): string | null;
export function mergeConfigs(yamlConfig: DevLoopConfig, cliConfig: Partial<DevLoopConfig>): DevLoopConfig;
```

### 4.3 CLI Integration

```bash
/dev goal "实现模块" --from-config           # auto-detect .pidev.yml
/dev goal "实现模块" --from-config ./path.yml # explicit path
/dev goal "实现模块" --from-config --verify "bun test"  # merge, CLI wins
```

Logic in `/dev goal` handler:
1. Parse `--from-config` → load YAML → normalize to `DevLoopConfig`
2. Parse remaining `--verify` flags → `parseInlineVerifies`
3. If both exist: `mergeConfigs(yamlConfig, cliOverrides)` — CLI overrides YAML
4. `buildConfig({ ...merged, maxIterations })`

### 4.4 `{files}` Template Expansion

In `packImplTask`, before embedding verify commands:

```typescript
export function expandCommand(cmd: string, changedFiles: string[]): string {
  return cmd.replace(/\{files\}/g, changedFiles.join(" "));
}
```

Expansion happens at task-packing time. The `changedFiles` list is the current iteration's cumulative changes (passed by the orchestrator).

## 5. Git Auto-Snapshot & Regression Rollback

### 5.1 New Module: `src/git.ts`

```typescript
import { execSync } from "node:child_process";

export interface GitSnapshot {
  hash: string;
  branch: string;
  timestamp: number;
}

/**
 * Create a snapshot commit of all current changes.
 * Uses a prefixed commit message for later identification.
 */
export function takeSnapshot(prefix: string): GitSnapshot;

/**
 * Hard-reset to a specific snapshot hash.
 */
export function rollbackToSnapshot(hash: string): void;

/**
 * Check if working tree has uncommitted changes.
 */
export function hasUncommittedChanges(): boolean;

/**
 * Prune old auto-snapshots, keeping the most recent `keep` count.
 */
export function pruneSnapshots(keep: number): void;
```

### 5.2 Integration Points

**Pre-iteration snapshot** (before subagent work — in dev_control "next" before returning):

```typescript
if (state.config.guardrails.gitAutoSnapshot && hasUncommittedChanges()) {
  const snap = takeSnapshot(`dev-loop: pre-iter-${state.currentStep + 1}`);
  state.latestSnapshot = snap.hash;
  if (!state.lastCleanSnapshot) state.lastCleanSnapshot = snap.hash;
}
```

**Regression rollback** (in Step 7 of decision engine):

```typescript
if (progress === "regression" && state.config.guardrails.rollbackOnRegression) {
  if (state.lastCleanSnapshot) {
    rollbackToSnapshot(state.lastCleanSnapshot);
  }
}
```

**Post-progress clean snapshot**:

```typescript
if (progress === "progress" && state.config.guardrails.gitAutoSnapshot) {
  state.lastCleanSnapshot = state.latestSnapshot;
}
```

## 6. User Experience Improvements

### 6.1 `ask_user` Verifier

When `dev_control("next")` determines a `main`-type verify step exists (i.e., `ask_user`), and the decision is to advance:

1. Instead of scheduling the next iteration via steer, the loop pauses
2. The user receives a message asking for confirmation
3. `/dev resume` restarts the iteration flow

Implementation:

```typescript
const mainSteps = state.config.verifySteps.filter(v => v.runsOn === "main");
if (mainSteps.length > 0 && !state.pauseReason) {
  // Pause and ask user
  state.active = false; // temporarily inactive
  // The resume handler will call buildIterationPrompt and send steer
  return {
    content: [{ type: "text", text: `⏸ Paused for user confirmation.` }],
    details: { state: toSnapshot(state), awaitingUser: true },
  };
}
```

The user's `/dev resume` triggers:
```typescript
state.active = true;
pi.sendUserMessage(buildIterationPrompt(state));
```

### 6.2 TUI Widget Improvement

Current:
```
┌─ Dev Loop: goal ────────
│ 实现注册模块
│ iter 3 (2 errors)
└─────────────────────────

Improved — shows error breakdown with a progress bar:

### 6.3 `/dev history` Command

Reconstructs all iterations from the session branch by scanning `dev_control` tool calls:

```

→ Iteration 2: Fixed type error in user.ts (regression: 0, progress: 1)

Implementation: reuses the existing `reconstructState` pattern — iterate `getBranch()`, collect `dev_control` tool results, format.

## 7. Edge Cases & Guards

| Scenario | Handling |
|----------|----------|
| `implSubagents` array is empty | Reject: `blockReason = "no_subagents"` |
| All `verificationPassed` are false | Reject: don't advance, don't touch registry |
| Some subagents pass, some fail | Reject: require all pass |
| `errorsFixed` and `errorsRemaining` contain same ID | `errorsRemaining` wins (verified still present) |
| max iterations reached, then resume | Continue but warn; 2x = force stop |
| `--from-config` + `--verify` both given | CLI overrides YAML per-field |
| No verify steps at all | Allow start, but emit warning |
| YAML file not found | `loadConfigFromFile` returns null, fallback to defaults |
| Git snapshot fails (dirty repo, merge conflict) | Soft fail — log warning, continue without snapshot |
| Regression rollback on a detached HEAD | Allow — `git reset --hard` works regardless |
